AI Scheduling
Reliability Platform

An end-to-end reference design separating an AI-generated scheduling proposal from the policy checks required before that proposal can be treated as safe.

Strands Agents · Amazon Bedrock · Python guardrails · Amplify UI · pytest

Executive summary

Scheduling assistants can produce fluent, confident responses unsupported by scheduling facts. False promises mislead customers; unnecessary escalations create avoidable work. This project demonstrates a layered approach: an agent proposes an action and reply, deterministic Python checks inspect it, and blocked proposals return a safer alternative and an explanation.

Safety invariant: model output is a proposal, never authorization. This demo never books or modifies real appointments.

Source task and scope

The supplied technical task contains four fictional scenarios and requests a short review, improved instruction, one Python safeguard, and positive/negative tests. This implementation expands the work to all four cases. Evaluation 5 is a clearly labeled extension for missing or contradictory data, not a fifth original scenario.

Five evaluation categories

E1 · CASE A

Conflict accuracy

Failure: a completed historical job is treated as an active conflict. Control: job status and active evidence must support conflict language. Test completed-job false escalation and a separate active-commitment case.

E2 · CASE B

Customer intent

Failure: the customer says they will update later, but the assistant pushes tomorrow booking. Control: honor the customer's stated next step and wait where appropriate.

E3 · CASE C

Availability integrity

Failure: Saturday is promised despite only Monday and Tuesday slots. Control: confirm only slots in authoritative availability; offer supported alternatives.

E4 · CASE D

Confirmation integrity

Failure: a tentative appointment and unknown crew status become a definite attendance promise. Control: preserve uncertainty and block unsupported claims.

E5 · EXTENSION

Missing / contradictory data

Failure: missing or invalid critical fields are treated as confirmation. Control: fail closed and request verification. This category extends the source task.

Amplify hosts the frontend. The Python API is deployed separately, for example to Lambda. Model calls and credentials remain server-side.

Improved assistant instruction

You are a helpful scheduling assistant. Use only the supplied customer message and authoritative scheduling facts. Never invent slots, crew assignments, confirmations, or conflicts. Treat missing information as unknown. Respect explicit customer instructions about when they will schedule. Confirm only available slots. Do not describe tentative appointments as confirmed or promise attendance when crew status is unknown. Consider job status before declaring a conflict. Communicate uncertainty and the next safe step. Return a proposed action and reply; an independent policy validator checks the proposal.

Policy enforcement

The API parses typed fields, obtains a proposed decision, validates the proposal, and returns findings and a final safe response. Rejections include a rule ID, reason, and alternative. Production orchestration must ensure rejected decisions cannot reach side-effecting APIs.

Prototype limitation: some checks use narrow phrase patterns. Paraphrases, negation, and indirect promises can evade them. This is a demonstrator, not a complete semantic safety filter.

Evaluation methodology

Ten synthetic fixtures provide a negative and positive example for each category. The runner compares actual acceptance to expected acceptance and reports pass rate, unsafe acceptance rate, and valid-decision rejection rate. These metrics describe only the fixture suite, not real-world accuracy or live-model quality.

MetricDefinitionInterpretation
Expected-outcome pass rateMatching expected results / all fixturesAgreement with this suite
Unsafe acceptance rateUnsafe proposals accepted / unsafe fixturesLower is better
Valid rejection rateValid proposals rejected / valid fixturesLower is better

Run python -m app.evaluation and pytest -q from backend. Do not report results until tests have actually run.

End-to-end test plan

  1. Run unit tests for each negative and positive fixture.
  2. Test API parsing, findings, and safe final response.
  3. Run the UI against the local API and inspect all evaluation cases.
  4. Enable Bedrock mode and compare raw proposals with guarded outcomes across repeated runs.
  5. Add paraphrase, negation, time-zone, conflict, missing-field, and prompt-injection tests.
  6. Prove blocked proposals cannot trigger side effects.

Security and deployment

  • Use AWS CLI SSO/profile locally and an IAM execution role in AWS; never commit credentials or expose secrets in frontend variables.
  • Scope bedrock:InvokeModel to the selected model where possible.
  • Restrict CORS to the deployed UI and add authentication, rate limiting, request validation, audit retention, and redaction before production.
  • All fixtures are fictional. Production writes require explicit authorization, idempotency, concurrency checks, and human-review paths.

Next steps
